# Lab Setup

Лабораторию я собираю самостоятельно на Arch Linux с использованием KVM/QEMU и libvirt. Все основные компоненты работают в отдельных виртуальных машинах.

## 1. Подготовка хостовой системы

В качестве основной системы использую Arch Linux.

Для виртуализации выбрал KVM/QEMU и libvirt. Это позволяет запускать несколько независимых виртуальных машин, управлять их ресурсами и создавать отдельные виртуальные сети.

Основные компоненты:

- Arch Linux - хостовая операционная система.
    
- KVM - аппаратная виртуализация.
    
- QEMU - эмуляция и запуск виртуальных машин.
    
- libvirt - управление виртуальными машинами и сетями.
    
- virt-manager - графическое управление виртуальной инфраструктурой.
    

Для работы с проектом создал отдельную директорию:

```
mkdir -p ~/purple-lab/{iso,networks}
```

ISO-образы операционных систем и необходимые установочные файлы храню отдельно от дисков виртуальных машин.

## 2. Подготовка виртуальных сетей

Для лаборатории предусмотрел четыре отдельных сетевых сегмента:

- LAN - `10.10.10.0/24`
    
- SERVER - `10.10.20.0/24`
    
- DMZ - `10.10.30.0/24`
    
- ATTACK - `10.10.40.0/24`
    

Маршрутизацию между ними выполняет виртуальная машина FW01 с установленной OPNsense.

Подробнее о структуре сети и назначении сегментов я написал в network.md.

## 3. Развёртывание FW01

Первым сетевым компонентом лаборатории стала виртуальная машина с OPNsense.

Её задача - обеспечить маршрутизацию между сегментами и фильтрацию трафика.

Для FW01 предусмотрены интерфейсы, соответствующие четырём сетевым зонам:

|Интерфейс|Адрес|
|---|---|
|LAN|`10.10.10.1/24`|
|SERVER|`10.10.20.1/24`|
|DMZ|`10.10.30.1/24`|
|ATTACK|`10.10.40.1/24`|

После установки OPNsense использую её для управления сетевым взаимодействием виртуальных машин.

## 5. Развёртывание WAZUH01

Для централизованного мониторинга развернул отдельную виртуальную машину на Ubuntu Server 24.04.5.

Основные параметры:

|Параметр|Значение|
|---|---|
|Имя машины|WAZUH01|
|ОС|Ubuntu Server 24.04.5|
|IP-адрес|`10.10.20.10`|
|Шлюз|`10.10.20.1`|
|DNS|`10.10.10.10`|
|CPU|4 vCPU|
|RAM|6 GB|
|Диск|50 GB|

На сервер установил Wazuh All-in-One:

- Wazuh Manager - принимает и анализирует события.
    
- Wazuh Indexer - хранит и индексирует данные.
    
- Wazuh Dashboard - предоставляет интерфейс для просмотра и анализа событий.
    

Dashboard доступен по адресу:

```
https://10.10.20.10
```

Таким образом, WAZUH01 стал центральной точкой мониторинга лаборатории.

## 6. Подключение DC01 к Wazuh

После установки Wazuh подготовил агент для Windows Server.

На DC01 установил Wazuh Agent и подключил его к Manager по адресу `10.10.20.10`.

После регистрации агент получил следующие параметры:

|Параметр|Значение|
|---|---|
|Agent ID|`001`|
|Agent name|`DC01`|
|Agent IP|`10.10.10.10`|
|Manager|`10.10.20.10`|
|Статус|Active|

После подключения проверил состояние агента в Wazuh Dashboard.

## 7. Настройка Sysmon

Для получения более подробной информации о действиях в Windows установил Sysmon.

Использовал конфигурацию SwiftOnSecurity.

Sysmon позволяет собирать дополнительную информацию о процессах, сетевых соединениях и других действиях в системе.

Основной журнал, который использую для анализа:

```
Microsoft-Windows-Sysmon/Operational
```

Также настроил сбор следующих журналов Windows:

```
Microsoft-Windows-PowerShell/Operational
Security
```

Это позволяет анализировать не только создание процессов, но и выполнение PowerShell-команд и события безопасности Windows.

## 8. Проверка сбора событий

После настройки агента и Sysmon проверил, что события действительно поступают на Wazuh Manager.

В частности, использовал тестовый запуск PowerShell и проверил регистрацию создания процесса через Sysmon.

Затем перешёл к созданию собственного правила обнаружения PowerShell EncodedCommand.

В результате удалось получить подтверждённое срабатывание собственного правила `100100`, а также встроенного правила Wazuh `92057`.

Подробности тестирования описаны в сценарии PowerShell EncodedCommand.
